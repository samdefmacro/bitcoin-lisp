# Next wave — 2026-08-22: bitcoin-lisp against Bitcoin Core, and what to build next

Compiled from: the tree at `1a7c6f8` (main, 398 PRs), Core master `d3056bc`
(2026-03-09, 30.99), the two live nodes' last recorded state (2026-08-21),
`docs/next-tasks-2026-08-20.md`, `docs/ga9-s3-verification-2026-08-21.md`, a
mechanical surface diff computed today (RPC names, P2P message types,
command-line options, BIPs, exported-symbol call counts) and four targeted
read-only audits of both source trees (P2P, validation/mempool/mining,
wallet/RPC, and a feasibility study of running Core's functional-test
framework against this node). Every claim below cites file:line on both
sides or says NOT REACHED.

## 0. The recommendation in one table

The thesis: after nine gap analyses the consensus layer is at parity and the
remaining defects are (a) code that exists but is not wired, (b) behaviour
only an external peer or client ever exercises, and (c) performance. All three
share a root cause: **the project has no behavioural oracle** — the 30k-check
unit suite has found none of the eight "correct code nothing calls" bugs, and
this research adds at least three more of the same shape. The wave should
therefore build the oracle while fixing what the research already found.

| Track | What | Size | Why first |
|---|---|---|---|
| **A. Wire what exists** | notfound disclaims; `CBlockUndo` → `rev*.dat`; compact-block serving; addr-relay gating; `submitblock` witness nonce; BIP54 relay cap + coinbase prep; ping timeout; feefilter range; services/proto-version gates; `getpeerinfo.addrbind`; `getnetworkinfo.version`; named RPC params; `-rpcallowip` + `-rpcauth` + 503 work queue instead of 429 | ~15 S items, 2 M | Each is a verified defect a Core peer or miner can observe today; most of the code is already written and tested |
| **B. Conformance harness** | run Bitcoin Core's `test/functional` against bitcoin-lisp: wrapper binary, option allow-list, named RPC params, `setmocktime`, default `debug.log`, Core datadir layout | P0 2-3 days → first tests green; P1 ~3-5 weeks → ~100 green | Turns 263 Core tests into an independent behavioural oracle; every red test is a finding of exactly the class the unit suite cannot see |
| **C. Performance** | re-profile on current main; parallel script validation done Core's way (coins prefetched on the main thread, persistent worker pool); sigcache key + erase-on-block; RPC up before mempool replay and index catch-up | M each | Mainnet IBD took 8 days; block validation is single-threaded; two startup paths keep RPC down for minutes |
| **D. Operator surface** | the ~30 operator-critical Core options we lack, `-whitelist`/permissions, log categories, `RPC_IN_WARMUP`, `getblocktemplate` cache/proposal/rules, `getblock` verbosity 3 + prevout/fee, `decodepsbt` BIP371, the five REST endpoints, CPFP bump fees in coin selection, `txospenderindex`, eviction passes, cmpctblock admission gates, Core-format `mempool.dat` | S-M each | Silent divergences that present as "node X can't be run/used like Core" |

Not recommended yet: I2P transport, versionbits machinery, Erlay interop
verification, a 10th gap analysis (track B *is* the verification pass).

### 2.4 Performance

- **Mainnet pruned IBD took 8 days** (2026-06-06 → 06-14): 1.6-1.7 blocks/s at
  h 680k-830k, 0.7-1.0 b/s by h≈888k. Core on comparable hardware completes a
  pruned mainnet IBD in well under a day. The June profile at h=828k: ~50% of
  one core, LevelDB reads dominant, secp256k1 not in the top frames — but that
  predates the flat-file store (#380-#393), the coins-DB best-block move
  (#335-#338) and the LevelDB `max-open-files` change (#351). Nothing has been
  re-profiled since.
- **Block script validation is single-threaded.** `*parallel-block-validation*`
  (src/config.lisp:218) defaults to NIL; its docstring blames SBCL's alien-type
  cache under concurrent libsecp CFFI. The crash record (memory: mainnet tip
  crash, resolved 2026-06-15) says the root cause was SBCL 2.1.11's
  multithreaded GC, fixed by building 2.6.5 — serial validation was a ~90×
  mitigation on the OLD runtime and has never been re-tried on 2.6.5.
  Two real problems remain in the parallel path as written, and both are
  design, not runtime:
  1. `validate-block-scripts-parallel` spawns `+parallel-validation-workers+`
     fresh threads **per block** (src/validation/block.lisp:714); Core keeps one
     persistent `CCheckQueue` pool (checkqueue.h, `-par`).
  2. The workers call `validate-tx-scripts` → `collect-spent-utxos` →
     `get-utxo` (coins-view-cache.lisp:602-607), whose read path **inserts on
     miss** into `cvc-entries` (`fetch-coin`, :160-168) — a plain, non-
     `:synchronized` SBCL hash table (`make-utxo-key-hash-table`,
     utxo.lisp:147). Concurrent read-through inserts corrupt the table
     regardless of any alien-type theory. Core's workers never touch the coins
     view: `ConnectBlock` copies each spent `Coin` into its `CScriptCheck`
     before queuing (validation.cpp ~:2540-2560).
  The fix is therefore Core's shape: prefetch the spent coins on the
  validation thread, hand workers pure data, keep a persistent pool, enable
  with `-par`, soak on testnet4 then mainnet.
- **Sigcache** keys include the comma-separated flag string and entries are
  never erased (interop.lisp:548-577; 2×65536 entries :489-495). Core keys on
  a salted SHA256 of (sighash‖pubkey‖sig) with no flags and erases on block
  connect (sigcache.h:41; sigcache.cpp:67, 80). Block connect hits only entries
  written by the second mempool pass, and only because tip+0 and tip+1 flag
  strings coincide today. The flag STRING representation is also GA9 C5's race
  and the cause of the empty-witness test trap — the bitfield fix serves both.
- No per-wtxid script-execution cache (validation.cpp:2027-2032).
- **Startup keeps RPC down.** Ours: fee stats → `mempool.dat` replay →
  banlist → anchors → txindex catch-up → *then* `start-rpc-server`
  (node.lisp:2488-2665). Core starts RPC at init step 4a before the chainstate
  loads (init.cpp:754-759), syncs indexes in background threads (:2040) and
  replays the mempool inside the import thread (:2047). Both recorded outages
  (83 MB mempool.dat → 45 min; txindex rescan → 9 min) are this ordering.

### 2.5 Consensus-adjacent (the only item in this class)

- **Assumevalid skip predicate is a superset of Core's.** Core skips script
  checks only when six conditions hold, including that the block is on the
  best-header chain, the chain work exceeds `nMinimumChainWork`, and the
  assumevalid block is at least two weeks of work ahead (validation.cpp:2320-2337).
  Ours checks ancestor-of-assumevalid only (block.lisp:1011-1059, the omissions
  are documented). Within the last two weeks of work below the assumevalid
  block we skip where Core verifies. M; carried from GA9 S2-3's deferral.

## 4. The strategic gap: a behavioural oracle

Eight "correct code nothing calls" bugs, all found by live logs or shipped
diagnostics; this research adds the notfound disclaims, the undo codec, the
compact-block serializer and the addr-relay flag. The unit suite cannot see
this class because it tests functions, not the node.

Bitcoin Core's `test/functional/` (263 tests) drives a real node over RPC and
P2P and asserts Core's behaviour. The feasibility study (session scratch report; its conclusions are
reproduced here) concludes **feasible with caveats**: the transport is
already Core-shaped, so the gap is plumbing, not architecture.

## 6. Method notes

- Mechanical diffs were computed with host grep before any agent ran and are
  reproducible from the commands in this document's history (RPC names via
  `^(static )?RPCHelpMan name(`, options via `AddArg("-…`, message types via
  `protocol.h`, exports via `#:sym` in the package files).
- Five concurrent deep-read agents, three of which spawned their own children,
  all hit the session limit within 30 minutes and returned nothing. Resumed
  two at a time with sub-agent spawning forbidden, each finished in 2-3
  minutes at 190-300k tokens. Recorded in memory as the operating rule.
- The storage/lifecycle dimension was covered from the main session with
  targeted reads instead of an agent; §2.4's startup-ordering and §2.6's
  layout facts come from there.
- Every agent finding used in §2 was spot-checked against the tree before
  inclusion (notfound disclaims, undo codec, `write-compact-block`, named
  params, the coins-cache insert-on-miss, the witness-nonce check).
