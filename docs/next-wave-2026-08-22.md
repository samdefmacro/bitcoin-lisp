## 0. The recommendation in one table

The thesis: nine gap analyses have taken the consensus layer *close* to parity,
but this round still found an anyone-constructible chain split (§2.1) — that is
the first thing to fix. Everything else divides into (a) code that exists but is
not wired, (b) behaviour only an external peer or client ever exercises, (c)
performance, and (d) the project not being usable by a second person. The first
three share a root cause: **there is no behavioural oracle.** The 30k-check unit
suite found none of the eight "correct code nothing calls" bugs, and this
research adds four more of the same shape. The wave should therefore build the
oracle while fixing what the research already found.

## 2. What this research found

Grouped by what an outside party would observe. "Wired?" marks the
"correct code nothing calls" pattern.

### 2.1 Consensus

**S1 — we reject a spend Bitcoin Core accepts. Anyone can construct it.**

Core takes the P2SH redeem script for witness detection from the **stack top
after evaluating the scriptSig**, then pops it:

```cpp
const valtype& pubKeySerialized = stack.back();
CScript pubKey2(pubKeySerialized.begin(), pubKeySerialized.end());
popstack(stack);
...
if (pubKey2.IsWitnessProgram(witnessversion, witnessprogram)) { ... }
```
(interpreter.cpp:2065-2081)

Our two halves disagree about what the redeem script is:

- the Coalton engine does it **correctly** — `validate-p2sh-with-tx` pops the
  stack top, hashes it, and executes it (src/coalton/script.lisp:2432-2443);
- but `verify-script`'s step 6 re-derives it from the raw bytes with
  `extract-last-push-data` (src/coalton/interop.lisp:725), and that helper
  recognises only opcodes `0x01-0x4b`, `OP_PUSHDATA1` and `OP_PUSHDATA2`. Every
  other opcode — including **`OP_0`**, `OP_1NEGATE` and `OP_1`-`OP_16`, all of
  which push — falls through its `(t (incf pos))` arm and does not update
  `last-push` (interop.lisp:772-797).

A concrete divergent input: pay to `P2SH(hash160(<empty script>))` and spend it
with `scriptSig = <push22: 0014{20 bytes}> OP_0` and an empty witness. The
scriptSig is push-only, so BIP16 is satisfied.

- **Core**: `stack.back()` is the empty element, so `pubKey2` is the empty
  script, which is not a witness program. `hadWitness` stays false, the empty
  redeem script executes as a no-op, the 22-byte element remains on the stack,
  `CastToBool` is true → **ACCEPT**.
- **Ours**: `extract-last-push-data` steps over the trailing `OP_0` and returns
  the 22-byte element, which *is* a v0 witness program. `had-witness` is set,
  and the canonical-push comparison (interop.lisp:740-746) compares the whole
  24-byte scriptSig against the 23-byte `[len][program]` → mismatch →
  `:witness-malleated-p2sh` → **REJECT**.

`SCRIPT_VERIFY_WITNESS` is mandatory in block validation, so this is not a
relay disagreement: a miner including such a spend produces a block we reject
and Core accepts — a chain split, costing an attacker one dust output. The
comment above the comparison shows the trap was understood; the bug is that the
detection reads the scriptSig instead of the stack the engine already computed.

The fix is to have `run-scripts-with-p2sh` surface the redeem script the
Coalton engine popped and use *that* in step 6 — deleting the second, divergent
derivation rather than patching `extract-last-push-data`. ~15 lines, and the
regression test is the vector above.

*Verified by reading all four paths (our step 6, `extract-last-push-data`, the
Coalton P2SH branch, Core's `VerifyScript`); not yet demonstrated by an
executed differential test — the fix PR must ship one.*

**S3 (historical) — the single-CHECKSIG `FindAndDelete` pattern.**
`strip-sigs-from-script-code` (interop.lisp:2456-2486) builds the correct
`CScript() << vchSig` encoding at every size, but the single-CHECKSIG path
(interop.lisp:2210-2216) builds `[len][sig]` only for `len <= 75` and searches
for the **bare signature with no push prefix** above that, where Core uses
`4c 4c <sig>` (interpreter.cpp:330). A scriptCode containing `4c 4c ‖ S` for a
76-byte `S` therefore has 78 bytes deleted by Core and nothing deleted by us →
a different legacy sighash. Reachable only below BIP66 activation (mainnet
363,725), where `ecdsa_signature_parse_der_lax` accepted padded DER; whether
any historical block actually contains one is NOT REACHED. A default IBD skips
these script checks under assumevalid, so this bites a `-noassumevalid` or
full-verification sync.

The same helper's CONST_SCRIPTCODE guard (interop.lisp:2176-2181) uses a plain
`search` over the bytes where Core gates on the boundary-aware
`FindAndDelete`'s count (interpreter.cpp:330-331), so we reject as non-standard
some transactions Core relays — policy only, and the guard is silently skipped
entirely for signatures over 75 bytes. Both defects are one fix: route
everything through a shared canonical-push helper and use `find-and-delete`'s
count.

**Assumevalid skip predicate is a superset of Core's.** Core skips script
checks only when six conditions hold, including that the block is on the
best-header chain, that chain work exceeds `nMinimumChainWork`, and that the
assumevalid block is at least two weeks of work ahead
(validation.cpp:2320-2337). Ours checks ancestor-of-assumevalid only
(block.lisp:1011-1059; the omissions are documented). Within the last two weeks
of work below the assumevalid block we skip where Core verifies. M; carried
from GA9 S2-3's deferral.

**Addrman and eclipse resistance** (three findings, all previously NOT REACHED):

- **`anchors.dat` is never consumed.** Core's `ReadAnchors` ends with an
  *unconditional* `fs::remove` — even on a deserialization exception
  (addrdb.cpp:234-246) — precisely so a crash loop cannot pin an
  already-eclipsed node to the same two block-relay peers. `load-anchors`
  (node.lisp:4114-4135) reads and leaves the file; it is only rewritten on a
  clean shutdown (:4110). After any unclean exit we re-dial the same anchors on
  every restart, forever. One line to fix.
- **`address-routable-p` accepts nine address classes Core rejects**
  (addrman.lisp:158-171 vs netaddress.cpp:398-465). We check only length,
  all-zero, the CJDNS `0xFC` prefix, and IPv6 `fc00::/7`. Core additionally
  excludes `::1`, `fe80::/10` link-local, `2001:db8::/32` documentation,
  ORCHID and ORCHIDv2, `127.0.0.0/8`, `169.254/16`, `100.64/10`, `198.18/15`
  and TEST-NET. We store, dial and **re-gossip** all of them, so an attacker
  can flood our buckets with `2001:db8::/32` addresses that cost Core nothing
  to drop. The docstring's deliberate divergence covers only IPv4 RFC1918.
- **Tried-table collision resolution and netgroup diversity both run only at
  startup.** `resolve-tried-collisions` (addrman.lisp:538-561) has one caller,
  inside `connect-to-peers` (node.lisp:4261), which by its own comment runs
  only at startup and when the peer count hits zero; Core calls
  `ResolveCollisions()` once per `ThreadOpenConnections` iteration
  (net.cpp:2768) and drives test-before-evict from the feeler via
  `SelectTriedCollision` (:2799) — for which we have **no equivalent at all**.
  Once the collision set reaches `+addrman-set-tried-collision-size+` = 10
  (addrman.lisp:25, 437-439), `address-book-good` returns NIL forever and the
  tried table stops learning from successful connections for the life of the
  process. Meanwhile `diversify-by-netgroup` is applied only in
  `connect-to-peers` (node.lisp:4324-4330) and not in
  `replace-disconnected-peers` (:4539-4646), where Core rebuilds
  `outbound_ipv46_peer_netgroups` every iteration (net.cpp:2651, 2685, 2826).
  After hours of churn the outbound set can concentrate in one /16 with nothing
  correcting it — and an ossified tried table plus undiversified outbounds are
  the two preconditions for an eclipse.

### 2.5 Performance

- **Mainnet pruned IBD took 8 days** (2026-06-06 → 06-14): 1.6-1.7 blocks/s at
  h 680k-830k, 0.7-1.0 b/s by h≈888k. Core on comparable hardware completes a
  pruned mainnet IBD in well under a day. The June profile at h=828k: ~50% of
  one core, LevelDB reads dominant, secp256k1 not in the top frames — but that
  predates the flat-file store (#380-#393), the coins-DB best-block move
  (#335-#338) and the LevelDB `max-open-files` change (#351). Nothing has been
  re-profiled since.
- **Block script validation is single-threaded.** `*parallel-block-validation*`
  (src/config.lisp:218) defaults to NIL; its docstring blames SBCL's alien-type
  cache under concurrent libsecp CFFI. The crash record (memory: mainnet tip
  crash, resolved 2026-06-15) says the root cause was SBCL 2.1.11's
  multithreaded GC, fixed by building 2.6.5 — serial validation was a ~90×
  mitigation on the OLD runtime and has never been re-tried on 2.6.5.
  Two real problems remain in the parallel path as written, and both are
  design, not runtime:
  1. `validate-block-scripts-parallel` spawns `+parallel-validation-workers+`
     fresh threads **per block** (src/validation/block.lisp:714); Core keeps one
     persistent `CCheckQueue` pool (checkqueue.h, `-par`).
  2. The workers call `validate-tx-scripts` → `collect-spent-utxos` →
     `get-utxo` (coins-view-cache.lisp:602-607), whose read path **inserts on
     miss** into `cvc-entries` (`fetch-coin`, :160-168) — a plain, non-
     `:synchronized` SBCL hash table (`make-utxo-key-hash-table`,
     utxo.lisp:147). Concurrent read-through inserts corrupt the table
     regardless of any alien-type theory. Core's workers never touch the coins
     view: `ConnectBlock` copies each spent `Coin` into its `CScriptCheck`
     before queuing (validation.cpp ~:2540-2560).
  The fix is therefore Core's shape: prefetch the spent coins on the
  validation thread, hand workers pure data, keep a persistent pool, enable
  with `-par`, soak on testnet4 then mainnet.
- **Sigcache** keys include the comma-separated flag string and entries are
  never erased (interop.lisp:548-577; 2×65536 entries :489-495). Core keys on
  a salted SHA256 of (sighash‖pubkey‖sig) with no flags and erases on block
  connect (sigcache.h:41; sigcache.cpp:67, 80). Block connect hits only entries
  written by the second mempool pass, and only because tip+0 and tip+1 flag
  strings coincide today. The flag STRING representation is also GA9 C5's race
  and the cause of the empty-witness test trap — the bitfield fix serves both.
- No per-wtxid script-execution cache (validation.cpp:2027-2032).
- **Startup keeps RPC down.** Ours: fee stats → `mempool.dat` replay →
  banlist → anchors → txindex catch-up → *then* `start-rpc-server`
  (node.lisp:2488-2665). Core starts RPC at init step 4a before the chainstate
  loads (init.cpp:754-759), syncs indexes in background threads (:2040) and
  replays the mempool inside the import thread (:2047). Both recorded outages
  (83 MB mempool.dat → 45 min; txindex rescan → 9 min) are this ordering.

Four items that earlier passes left open are now resolved:

- **`walletprocesspsbt` never upgrades `witness_utxo` to `non_witness_utxo`.**
  Core's `FillPSBT` attaches the full previous transaction whenever
  `!input.non_witness_utxo` — the presence of `witness_utxo` is irrelevant, and
  only an already-signed input is skipped (wallet.cpp:2201-2212); it is dropped
  again afterwards only when every input is segwit **v1** and none is
  ANYONECANPAY (psbt.cpp:514-549, `RemoveUnnecessaryTransactions`, which we
  also lack). Ours skips the input when *either* field is present
  (psbt.lisp:830-849, called from :1122). Our own creator paths do attach it
  (psbt.lisp:1268-1271; wallet-spend.lisp:2957-2963), so the gap is exactly the
  cosigner flow: import a Sparrow/Electrum/BDK PSBT, sign here. Trezor, Ledger
  and Coldcard refuse to sign segwit v0 without the full prev-tx — that is the
  2020 fee-spoofing defence, since `witness_utxo`'s amount is unauthenticated.
  Distinct from the GA9 fix, which was on the signing-precedence side. **S.**
- **Multipath descriptors `<0;1>` (BIP389) are rejected outright.**
  `%parse-key-path` hard-errors "Multipath descriptors are not supported"
  (descriptors.lisp:179-189, scope note at :16). Core expands them into N key
  paths (descriptor.cpp:1802-1851) and `importdescriptors` treats element 2 of
  a 2-element multipath as the internal descriptor (backup.cpp:227-233).
  `wpkh([fp/84h/0h/0h]xpub/<0;1>/*)` is the canonical export form of Sparrow,
  Ledger Live, BlueWallet, BDK and modern Core's own `listdescriptors`, so an
  affected wallet cannot be restored at all — not merely degraded. This is the
  largest user-visible interop gap in the wallet. **M** (G7-40).
- **A rescan freezes the passphrase relock deadline.** `wallet-unlocked-key`
  suppresses the inline relock while a scan holds the passphrase
  (wallet.lisp:283-286) and the sweeper cannot fire because it needs the wallet
  lock (wallet-crypt.lisp:427-440), yet `getwalletinfo` keeps reporting the
  original `unlocked_until` (wallet.lisp:1597-1598). Core's scheduled callback
  relocks and zeroes `nRelockTime` regardless of any scan
  (wallet/rpc/encrypt.cpp:102-110); the scanning flag only makes three RPCs
  refuse (:141, 206, 263). So on a long `rescanblockchain` the master key stays
  decrypted far past the user's timeout while the RPC says it already expired.
  **S.**
- **Coin selection has three of Core's four algorithms.** BnB
  (wallet-spend.lisp:954), Knapsack (:1091) and SRD (:1159) are present and the
  cascade matches line for line; **CoinGrinder is absent** (documented at
  :1229-1232), which Core runs whenever the effective feerate exceeds 3× the
  long-term feerate (spend.cpp:769-776). At high feerates we therefore pick
  heavier input sets than Core — larger fees, never invalid. **M**, and it
  pairs with G7-39's missing bump-fee discount (:1241-1242).

Web UI: P0-P4 and P6a-d shipped; P5 (SSE) not built; versus bitcoin-qt still
missing coin control, CSV export, log tail, a traffic graph and
payment-request history.

**Assumeutxo and reporting consistency**

- **`loadtxoutset` never writes the snapshot coins-DB best-block pointer**
  (GA9 S3, previously NOT REACHED — now CONFIRMED).
  `%populate-snapshot-chainstate` (methods.lisp:2368-2444) writes coins with
  `coins-view-batch-put` and never calls `coins-view-batch-set-best-block`.
  Core sets `coins_cache.SetBestBlock(base_blockhash)` (validation.cpp:5889)
  plus a `FORCE_FLUSH` (:5963) and deliberately stamps a `GetRandHash()` during
  streaming (:5871) so a crash mid-load cannot look valid. We do neither — so
  assumeutxo sits outside the invariant PRs #335-#338 established.
- **`gettxoutsetinfo` and `gettxout` report the chain tip, not the coins view's
  own best block** (GA9 C7 confirmed, and it extends to `gettxout`).
  methods.lisp:4666-4673 and :594-600 vs Core rpc/blockchain.cpp:1083, 1244.
  The coins view can already report its own best block
  (coins-view.lisp:205-212), so this is nearly a one-line fix — and it matters
  because `hash_serialized_3` *is* the assumeutxo commitment.
- **`leveldb-iter-check-error` guards 1 of 5 iterator scans** (leveldb.lisp:354;
  sole caller wallet-store.lisp:442). The two unchecked ones that matter are
  coins-view-cache.lisp:809 (backs `gettxoutsetinfo`/`dumptxoutset`) and
  coins-view.lisp:240 (the `reindex-chainstate` coin wipe). A mid-scan I/O
  error makes `leveldb-iter-valid-p` false, the loop simply ends, and a
  truncated UTXO set is reported as complete — or a partial wipe as done.

**Performance and layout**

- **LevelDB is opened with no block cache and no bloom filter.** Core sets
  `block_cache = NewLRUCache(nCacheSize/2)`, `write_buffer_size = nCacheSize/4`
  and `filter_policy = NewBloomFilterPolicy(10)` (dbwrapper.cpp:139-155), and
  splits `-dbcache` across the coins DB and each index (node/caches.cpp:57-72).
  Ours passes only `:max-open-files 1000` (coins-view.lisp:164) with a fixed
  4 MiB write buffer (leveldb.lisp:170-186), and `-dbcache` sizes only the
  in-memory coins cache (node.lisp:3111). Every negative coin lookup therefore
  reads a data block per SST level — and the June profile put
  `pread64`/`Table::Open` at the top. **This is the highest-value single
  change in track C.**
- **Block-index file positions are persisted but never populated.**
  `block-index-entry-file/data-pos/undo-pos` are written (chain.lisp:1001-1005),
  read back (:1377-1379) and used as change-detector bits (:911-912) — but
  nothing ever assigns them; they stay `-1`/`#xFFFFFFFF`. Positions are instead
  recovered at **every startup** by `%scan-flat-block-files` (blocks.lisp:298-345):
  at mainnet scale ~920k records × (`file-position` + two `read-sequence`) ≈ 1.8M
  syscalls, plus a `stat` per legacy per-block file (155,692 on testnet4,
  blocks.lisp:359-366). The 12 dead bytes per entry also inflate every full
  header-index rewrite.
- **No LevelDB obfuscation key** (G7-59 confirmed): Core writes a random 8-byte
  key at creation and XORs every value (dbwrapper.cpp:253-262, `.obfuscate=true`
  for the coins DB at validation.cpp:1921). Ours stores raw values
  (leveldb.lisp:252-318). The flat *block* files do have their XOR key
  (flatfile.lisp:100-120) — it is only the databases that lack it.
- **No prune locks**: Core registers `m_prune_locks` with a `PRUNE_LOCK_BUFFER`
  for blockfilterindex, coinstatsindex and assumeutxo (validation.cpp:2721-2734).
  We bound pruning only by `+min-blocks-to-keep+` and the snapshot floor
  (blocks.lisp:484-546), so an index lagging the tip can have its blocks pruned
  out from under it.
- **No persisted reindex-in-progress flag**: Core's `DB_REINDEX_FLAG 'R'`
  (blockstorage.cpp:61, 73-85) makes an interrupted `-reindex` resume as a
  reindex; ours silently resumes as a normal start. And our `-reindex` is
  *additive* — it extends the existing index (node.lisp:2350-2358) rather than
  wiping it, so a corrupt (as opposed to missing) `headerindex.dat` is not
  repaired by the flag that exists to repair it.
- **`pruneblockchain` is a no-op under the new block-file format.**
  `prune-block` refuses any block inside a flat file and log-warns
  (blocks.lisp:381-390); `prune-blocks-to-height` (:547) walks only legacy
  per-block files. Automatic pruning *does* handle flat files
  (`%prunable-flat-files`, :513). testnet4 runs flat files today and mainnet is
  the pruned node, so this is precisely the blocker for the planned flat-file
  rollout to mainnet — manual pruning would silently stop working. Cheap fix:
  reuse `%prunable-flat-files` from the manual path.
- **All three index catch-ups block startup**: `build-tx-index` (node.lisp:2562),
  `%catch-up-blockfilterindex` (:2584) and `%catch-up-coinstatsindex` (:2604)
  run synchronously before `start-rpc-server` (:2665), and the code comments the
  divergence at :2554-2558. Core syncs indexes on a background thread
  (index/base.cpp:453-457) and serves throughout. Note the 9 min → 9 s figure in
  the project's memory is the *resume* case; a from-scratch mainnet txindex is a
  whole-chain re-read.
- Crash recovery still probes coinbases and rewinds (`recover-inconsistent-chainstate`,
  node.lisp:979-1060) where Core rolls forward with `ReplayBlocks` using
  `DB_HEAD_BLOCKS` + undo (validation.cpp:4812-4889). Now that the `'B'`
  best-block key is written in the same batch as the coins, the probe is
  redundant.

**More unwired code** (adding to §2.2): `do-flush` (node.lisp:3377) has no
production caller — it is a dead *duplicate* of the bookkeeping
`maybe-periodic-flush` inlines at node.lisp:3433-3434, and two assumeutxo tests

**Cleared here**: the `headerindex.delta` crash window (a delta whose recorded

1142-1152); the `'B'` best-block key staged in the same writebatch as the coins

## 6. Method notes

- Mechanical diffs were computed with host grep before any agent ran and are
  reproducible from the commands in this document's history (RPC names via
  `^(static )?RPCHelpMan name(`, options via `AddArg("-…`, message types via
  `protocol.h`, exports via `#:sym` in the package files).
- Five concurrent deep-read agents, three of which spawned their own children,
  all hit the session limit within 30 minutes and returned nothing. Resumed two
  at a time with sub-agent spawning forbidden, each finished in 2-3 minutes at
  140-300k tokens. A second round of two agents closed the storage dimension
  and the accumulated "NOT REACHED" list the same way. Recorded in memory as
  the operating rule: **≤ 2-3 deep readers, no grandchildren.**
- Cheap mechanical work belongs in the main session, not an agent: the
  surface diffs, the exported-symbol sweep and the packaging facts in §2.9 were
  minutes of shell each.
- **Every finding used above was re-verified by hand before inclusion**, and
  that changed three of them:
  - the §2.1 chain split was re-derived from all four code paths — our step 6,
    `extract-last-push-data`, the Coalton P2SH branch and Core's `VerifyScript`
    — before being called a consensus bug;
  - `do-flush` was reported as an unwired flush wrapper, which would have meant
    broken flush bookkeeping; reading it showed `maybe-periodic-flush` inlines
    the same resets, so it is dead *duplication*, not a functional bug;
  - the claim that `scripts/docker-test.sh` cannot be trusted to report failure
    turned out to be stale — it exits non-zero on both failures and
    zero-selection today, which is what makes track E's CI item a thin wrapper
    rather than a project.
- Two things this document does **not** have: an executed differential test for
  the §2.1 split (the fix PR must ship one), and any performance measurement
  newer than June. Track C's first step is a benchmark for that reason.

### A note on the cold battery and machine load (2026-08-22)

Two tests in the cold battery drive REAL sockets on loopback —
`v2-transport-loopback-handshake-and-messages` (bip324-transport-tests) and
`inbound-handshake-loopback` (inbound-listening-tests) — and both fail
intermittently when the machine is busy, the second one first observed today.
Three consecutive runs of the SAME tree gave one failure, two failures (a
different test), then a clean 32,992/0/0 once the warm dev container was
stopped. The v2 one already carries 60-second timeouts and a comment recording
an earlier round of the same problem at 10 seconds, so raising the deadline
again is not the answer.

Practical rule: **stop the warm dev container before the verification-of-record
run.** A red battery from these two tests specifically, on a machine also
running a dev image or another agent's containers, is load — but it must be
re-run to clean rather than waved through, because the whole value of the cold
battery is that its result is trustworthy.

### What the implementation round changed about the research

Four items in this document were **wrong or incomplete** where they touched a
Core mechanism, and each was caught by review before shipping:

- §2.2 said Core's `notfound` arm calls `RemoveBlockRequest`. It does not — the
  arm is transaction-only. The fix was deletion, not wiring.
- Track A 6 read as a constants change. Setting the ping constants alone made
  the 20-minute timeout **unreachable**, because the shorter interval re-sent
  the ping and reset its clock.
- Track A 9a's "collision resolution runs only at startup" is true, but simply
  running it per tick would have made eclipse resistance **worse**: without
  Core's `SelectTriedCollision` probe, the only branch that can fire evicts an
  untested incumbent on a timer.

- Track B P0 read as plumbing. It is, but the plumbing is not the value: the
  first hour of running the binary the way the framework runs it produced three
  bugs the 32k-check unit suite cannot see — a `-datadir` without a trailing
  slash silently relocating the databases, hunchentoot's access log making
  stderr non-empty (which alone fails every test that stops a node), and a
  missing `wait` parameter on the one method every test calls. §4's claim that
  the unit suite "cannot see this class because it tests functions, not the
  node" is now measured rather than argued.
- Track D's `-rpcallowip` read as an option to parse and check. But adding it
  is what makes a non-loopback `-rpcbind` possible **for the first time**, and
  the property that had protected `/rest/` and `/ui/` was precisely that the
  acceptor was always loopback-only. Checking the ACL in `rpc-handler` — the
  obvious place, and where the first draft put it — would have left the REST
  surface and the web UI (default ON for every non-mainnet network) reachable
  from any address. The gate had to move to the acceptor, where Core's is.

The pattern is one rule: **when porting a Core mechanism, find every site Core
drives it from before shipping the first one.** A half-ported mechanism can be
worse than the gap it closes — and the `-rpcallowip` case adds a corollary:
check what the *absence* of the feature was silently guaranteeing, because
adding it can remove a protection nothing named.
